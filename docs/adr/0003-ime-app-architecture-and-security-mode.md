# 输入法应用架构:extension 承载全部功能 + 目标基础安全模式

**Status: accepted**

## 背景

拼音预测输入法(见 `CONTEXT.md`)是本仓库第一个应用工程,目前处于 grilling 设计阶段。IME Kit 官方文档明确了两个技术边界事实:

1. 主 UIAbility(应用主入口)想要和 `InputMethodExtensionAbility` 共享数据,必须申请 `data-group-id` 并配置共享沙箱,流程是登录 AppGallery Connect 提交材料(应用名称、appId、开发者Id 等),1~3 个工作日审核。个人开发者账号能否走通这条路、要多久,文档没有说明。
2. 输入法安全模式(基础模式 / 完整体验模式)是用户在系统设置里手动切换的开关,应用只能运行时查询当前处于哪个模式(`getSecurityMode`),无法主动声明或请求进入完整体验模式。

## 决定

1. **应用架构**:主 UIAbility 只做两件事——首次启动引导用户去系统设置里启用输入法、一个关于页面;不读写 `InputMethodExtensionAbility` 的任何数据。真正的功能(键盘、候选栏、以及设置/管理类交互,例如清除本地学习数据的入口)全部实现为 extension 自己 Panel 内的另一个 ArkUI 视图,通过状态切换进入,不使用共享沙箱,不申请 `data-group-id`。个性化数据只存在 extension 自己的独立沙箱里。
2. **目标安全模式**:基础模式。设计上不假设、不依赖任何只有完整体验模式才能使用的能力。

## 为什么

- 基础模式禁止的能力清单(网络、拉起其他 ability、访问隐私类接口等)里没有一项是这个应用真正需要的——应用本来就设计成本地、无网络、数据只存自己独立沙箱,选基础模式是零功能代价的选择。完整体验模式是用户手动切换的开关而非应用可请求的权限,因此从设计上就不能假设会拿到它。
- 共享沙箱方案(备选:extension + 独立设置 App)唯一的价值是"能做一个独立的设置 App 界面",但这个价值可以用 extension 自己的面板内视图切换完全替代——官方 `实现一个输入法应用` 指南所附的 Kika 示例本身就用状态变量在同一个 panel 里切换 `KeyMenu`/`NumberMenu`/`SymbolMenu`/`Submenu`/`EditView` 好几种视图,加一个"设置"视图是同一套模式的自然延伸,不是新发明。而共享沙箱需要的 AppGallery Connect 审批,对个人开发者账号能否走通、要多久都不确定,是一个不必要的外部依赖,会话卡开发节奏。
- 排除了"纯 extension、完全不含任何 UIAbility"这个选项:文档未确认 Stage 模型下 entry module 是否允许只声明一个 ExtensionAbility 而不含 UIAbility;即便技术可行,缺少首次启动引导用户去系统设置启用输入法的落脚点,也会造成实际的初次使用体验问题。

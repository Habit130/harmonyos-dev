# GitHub Flow 协作机制:分工细则

**Status: accepted**

## 背景

在 [ADR-0001](./0001-founding-rationale-and-division-of-labor.md) 确立的"人类设全局约束、AI 负责实现"总纲之下,GitHub Flow 的具体执行还需要明确:issue 如何变成代码、谁验收、谁合并、遇到分歧听谁的。

## 决定

**流程主干**:人类给出方向 → 通过 grilling 式讨论确定设计与约束 → 写入文档(PRD/issue,经 `to-prd` / `to-issues` skill)→ 人类手动把已发布的 issue 逐个交给独立的"弱 session"实现并开出/更新 PR → "强 agent"(主 session)对 PR 做验收。

**强/弱 agent 角色**

- **弱 session**:依据 issue 文档 + 仓库证据独立完成一个(或按依赖关系合并的多个)issue 的实现,不对自己的成果做终审。issue 粒度与分支/PR 粒度不强制一一对应,由发布 issue 时的判断决定,不强求 1 issue = 1 分支 = 1 PR。
- **强 agent**:对弱 session 提交的 PR 做验收,方式灵活(review、跑 `/code-review` 或 `/verify`、必要时用 `advisor` 二次确认),通过后按下方合并规则处理。

**Dispatch 默认人工**:issue 发布后,默认由人类手动把 issue 交给具体的弱 session 执行,强 agent 不自动派发 subagent。只有在人类显式批准(如 "ultracode" 或类似指令)时,强 agent 才可以自主用 Agent/Workflow 工具派发弱 session 并自行验收——完全自动化的批量推进容易导致错误累积,因此默认保留人工在每个 issue 启动这一环节的把关,这是权衡过的默认值,不是工具能力限制。主 session 可以在人类手动分派时提供简短的启动 prompt,但 issue 文档本身必须自包含,弱 session 不应依赖这个 prompt 之外的额外上下文。

**合并权限默认 AI 自主**:强 agent 验收通过后默认直接合并 PR 并关闭,不需要人类点头。仅当 PR 触及以下两类之一时,验收通过后打 `ready-for-human` 标签,交由人类执行实际合并(其余所有 PR 不使用这个标签):

1. 仓库自身的运行机制文件——即在开发的应用程序代码之外、支撑仓库/工作流本身运作的内容(`CLAUDE.md`、`docs/adr/*`、`docs/agents/*`、workflow 定义本身等)。
2. 安全相关或不可逆的内容(签名、凭证等,以及其他会造成不可逆后果的变更)。

**信息来源优先级**:弱/强 agent 在实现和验收时,证据权重从高到低:

1. 仓库开发文档证据(`docs/harmonyos-guides/` 等)
2. 人类与 AI 讨论得到的 issue/PRD 文档
3. AI 自主的细粒度补充(仍须遵守既有约定)

当 issue 文档与官方文档冲突时,以官方文档为准;agent 应在 PR 中标注这一偏离,而不是悄悄按 issue 原文实现,也不是悄悄改写 issue。

## 为什么

- Dispatch 环节保留人工,是在"完全自动化可能导致错误累积"与"推进效率"之间做的显式取舍,是可以随信任积累调整的开关,不是能力限制。
- 合并权限默认给 AI、只在两类内容上收紧,和 ADR-0001 的第一因一致:那两类恰好是"仓库如何运作"和"不可逆后果",都属于全局约束的范畴,而不是应用层技术架构,因此不违背"人类不做架构决策"这一条。这也与"高风险/难以撤销的操作需要人工确认"的通用原则自然吻合,不是额外发明的例外。
- 证据优先级把"已经沉淀的官方文档"放在"临时讨论出的 issue 表述"之上,是因为 issue 文字可能有疏漏而文档更权威;悄悄偏离 issue 会破坏"issue 即可独立完成的完整契约"这一前提,所以要求显式标注而不是默默纠正或默默照做。

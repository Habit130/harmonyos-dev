# 仓库第一因与人机分工总纲

**Status: accepted**

## 背景

本仓库最初以"HarmonyOS 学习仓库"命名和定位。经过讨论明确:学习的对象不是 ArkTS/HarmonyOS API 本身,而是通过 vibe coding(以 AI 为实现者)构建 HarmonyOS 应用的这一整套开发流程与人机协作框架。`docs/harmonyos-guides/` 是为 AI 实现提供准确、及时的 API 依据,不是给人类逐条阅读、用来学写代码的教材。

## 决定

- **仓库产出双重**:(1) 真实可运行的 HarmonyOS/ArkTS 应用;(2) 一套经过实践打磨的人机协作开发流程本身(GitHub Flow + issue 驱动 + 强/弱 agent 验收,细则见 [ADR-0002](./0002-github-flow-collaboration-mechanics.md))。人类要精进的是这套流程的运用能力,不是 ArkTS 编码能力本身。
- **人类角色**:设定全局层面的约束和方向,通过 grilling 式讨论参与应用层设计与疑难判断,并保留特定类别的把关权(见 ADR-0002)。人类不逐行编写业务代码,也不承担应用层技术架构的决策责任。
- **AI 角色**:负责代码开发,包括应用层技术架构、模块划分等具体实现决策;在既定约束和讨论结论之上把工作推进到底。

## 为什么

如果第一因是"人类要学会写 HarmonyOS 代码",那么"AI 拥有全部实现和架构自主权、人类不写代码"这个分工就自相矛盾。把第一因明确为"打磨 vibe coding 式的人机协作流程、产出真实应用",分工模型才自洽:人类的学习收获体现在方向判断、约束设定和设计评审的熟练度上,不是编码本身。

这一条是后续所有具体分工问题(合并权限、dispatch 方式、把关类别等)的推导起点——一旦第一因认定错误,下游所有分工决定都要重新审视,所以单独作为 ADR-0001 记录,而不是散落在各处的隐含假设。
